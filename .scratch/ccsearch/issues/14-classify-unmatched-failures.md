# Classify the `(no marker)` failures: grow the signature table, decide on harness noise

Status: ready-for-agent
Category: enhancement

## Why

`--stats` (issue 13) groups Failures by `(tool, matched FAILURE_MARKERS entry)`, falling back to a per-tool `(no marker)` bucket. Run against the real Store, **the three biggest groups are all `(no marker)`** (Bash 101, Edit 63, PowerShell 59 — roughly half of all Failures). So `stats` answers "what causes a lot of failures?" with a shrug for its largest buckets. `FAILURE_MARKERS` was built (issue 11) to pick a salient *display line*, where a last-line fallback is fine; as a *grouping signature* (ADR 0003) it under-classifies. ADR 0003 already named this future work — this is that work.

## What's actually in the catch-all (real-Store counts, 2026-06-02)

Two distinct populations, and they want different treatment:

**A. Legitimate tool Failures that simply match no marker** — these should be *classified*:
- `<tool_use_error>` wrapper — **189** occurrences; wraps the real message and currently defeats marker matching.
- `String to replace not found` (Edit) — **39**
- `has not been read yet` (Edit/Write/Read order-of-operations) — **~98** (count inflated by echoes; real but fewer)
- `exceeds maximum allowed tokens` (Read) — **21**
- `is not recognized` (PowerShell unknown cmdlet) — **7**
- `Blocked:` (harness command guard) — **9**

**B. "Failures" that arguably aren't a tool erroring at all** — these need a *decision*, not a marker:
- `tool use was rejected` / `doesn't want to proceed` (the user declined the call) — **~28**
- `temporarily unavailable` (model/classifier down, retryable infra) — **19**

## The design fork — RESOLVED 2026-06-02: **bucket with explicit labels** (option 3)

Population B was the open question. A `tool_result` with `is_error:true` for a *user rejection* or a *transient infra outage* fits the CONTEXT.md definition of **Failure** structurally, but not in spirit — the tool didn't error, the run was declined or the backend blinked. Options:

1. **Classify them** like everything else (add `rejected` / `unavailable` markers). Simple, consistent, but pollutes "what causes failures" with things that aren't code problems.
2. **Filter them out** of failure analysis entirely (both `--failed` and `--stats`). Cleaner signal, but `--failed` silently drops records that *are* `is_error:true` — needs to be a documented, predictable rule, and may warrant updating the **Failure** glossary entry in CONTEXT.md (and possibly an ADR, since it narrows a domain term).
3. **Separate bucket** — count them but under an explicit `rejected` / `unavailable` signature so they're visible but not conflated with real errors.

Decide this first; it changes the CONTEXT.md definition of Failure either way.

## Likely acceptance criteria (to firm up at triage)

- [ ] Strip `<tool_use_error>…</tool_use_error>` wrappers before signature/salient-line matching (a pure step, shared by `salient_line` and `failure_signature` so they stay consistent). Noted as pending since issue 11.
- [ ] Add population-A content markers to `FAILURE_MARKERS` (or a sibling table), in priority order, with a unit test per shape from the five real samples above. Keep it a fixed, documented lookup table — no fuzzy matching (the ADR 0002 / ADR 0003 principle).
- [ ] Resolve population B per the chosen fork option; update the **Failure** glossary in CONTEXT.md accordingly, and an ADR if the decision narrows the term.
- [ ] Re-run `--stats --all`; the `(no marker)` buckets should no longer dominate the top of the table (the regression check is the real Store, not a fixture).

## Out of scope

- No fuzzy/normalised similarity — still grouping by a fixed signature table, just a bigger/cleaner one. This issue grows the classifier; it does not change the grouping *mechanism* decided in ADR 0003.

## Agent Brief

**Category:** enhancement
**Summary:** Grow the failure-signature classifier so the dominant `(no marker)` buckets in `--stats` get legible, deterministic signatures — by stripping the `<tool_use_error>` wrapper, adding markers for real-but-unmarked tool errors, and giving harness-noise failures (user rejections, transient unavailability) their own labelled buckets.

**Current behavior:**
Failure analysis (`--failed` list and `--stats` table) classifies each Failure by the highest-priority entry of a fixed, priority-ordered marker table it matches, falling back to a single per-tool *no-marker* bucket (ADR 0003). Against the real Store the three largest `--stats` groups are all `(no marker)` — roughly half of all Failures — because: (a) many tool errors are wrapped in `<tool_use_error>…</tool_use_error>`, which the matcher never unwraps; (b) common tool-error messages (Edit "String to replace not found", Read "exceeds maximum allowed tokens", Read/Write/Edit "has not been read yet", PowerShell "is not recognized", harness "Blocked:") match no marker; and (c) non-error records that are structurally `is_error:true` — user-declined tool calls and transient model/classifier unavailability — also fall through to no-marker.

**Desired behavior:**
- The `<tool_use_error>…</tool_use_error>` wrapper is stripped before signature and salient-line matching, so the inner message drives classification. The list and the table must stay consistent (the same shared classifier feeds both — see Key interfaces).
- The marker table gains entries (Population A) for the common real tool errors observed in the Store: Edit's "String to replace not found", "has not been read yet", Read's "exceeds maximum allowed tokens", PowerShell's "is not recognized" (unknown cmdlet), and the harness "Blocked:" guard. These remain a fixed, documented, priority-ordered lookup table — **no fuzzy or normalised matching** (ADR 0002 / ADR 0003 principle).
- Harness-noise failures (Population B) are **bucketed, not filtered**: user-declined calls (`tool use was rejected` / "doesn't want to proceed") group under a `rejected` signature, and transient model/classifier outages ("temporarily unavailable") under an `unavailable` signature. They remain visible in both `--failed` and `--stats`; the `Failure` glossary definition in CONTEXT.md is unchanged.
- Displayed signatures are **clean labels**, not raw match substrings: the `--stats` table shows `rejected` and `unavailable` (and readable labels for Population A), never `tool use was rejected` or a long verbatim needle. This implies a signature entry can carry a display label distinct from the substring it matches on.

**Key interfaces (by contract, not location):**
- The fixed marker/signature table (currently `FAILURE_MARKERS: &[&str]`) — likely evolves so each entry pairs a *match needle* with a *display label* (e.g. a small struct), since Population B needs short labels that differ from the matched text. Priority ordering still decides ties.
- `failure_signature(error_text) -> Option<_>` and `salient_line(error_text) -> String` — must share the same wrapper-stripping and marker lookup so the list and table can never disagree about a Failure's class (this invariant already has a test; keep it green).
- `FailureGroup.signature` and `format_stats` — the signature carried into grouping and rendering should be the clean display label.
- A pure wrapper-stripping helper applied before matching; whether `--full` output also strips the tags is a minor display call (prefer stripping for readability).

**Acceptance criteria:**
- [ ] A `<tool_use_error>`-wrapped error is classified by its inner message, not dumped in `(no marker)`; covered by a unit test.
- [ ] Each Population A shape (Edit string-not-found, has-not-been-read, Read exceeds-maximum, PowerShell not-recognized, Blocked) has a unit test asserting its `failure_signature`, and `salient_line` still agrees with `failure_signature` on the marker.
- [ ] User rejections group under a `rejected` signature and transient unavailability under `unavailable`; both appear in `--stats` output with those exact labels (unit-tested), and remain present in `--failed` (not filtered).
- [ ] `format_stats` renders the clean label for every group; no raw verbatim needle or `<tool_use_error>` tag appears in the table.
- [ ] Regression check against the real Store (`cargo run -- --stats --all`): the `(no marker)` buckets no longer dominate the top of the table. (Manual/observational — the fixtures are the unit-level guarantee.)
- [ ] `cargo test` green and `cargo clippy --all-targets -- -D warnings` clean.

**Out of scope:**
- No fuzzy / normalised / token-masking similarity — this grows the fixed signature table only; the grouping *mechanism* from ADR 0003 (`(tool, signature)`) is unchanged.
- Do **not** filter any `is_error:true` record out of failure analysis; Population B is bucketed, not removed. The `Failure` definition in CONTEXT.md stays as-is.
- No new CLI flags; this is purely better classification behind the existing `--failed` / `--stats`.
